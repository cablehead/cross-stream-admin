The manifest is a record of booleans, and the three keys above are the only ones accepted: store, services (implies store), datastar. An unknown key or malformed nuon is rejected at push time, with the reason printed in your git push output. You declare intent, not raw flags.

Files

Your handler runs from repo/, sandboxed. Two rules cover nearly everything:

  • repo/ is disposable. Every push deletes it and re-extracts it from the pushed commit. Anything not in the commit is gone, and .gitignore does not protect it. Never write data you want to keep next to your code.
  • state/ is yours. Always present, writable, and untouched by deploys. Its path is $env.SITE_STATE. Put your SQLite file, caches, and uploads here. Removed only if you delete the site.

Everything else is read-only. The site directory itself is not writable, so state/ (and store/, if you enabled it) are the only durable places to write. /tmp works for scratch but is shared with the rest of the VM and does not survive a reboot.

SQLite works, including WAL mode, as long as the database lives directly in $env.SITE_STATE so its -wal and -shm siblings can be created beside it. Your site runs under a transient system user, so do not depend on file ownership, only on the directories above.

Platform

Useful if you want to commit a static binary to your repo and call it from your handler. That is the supported way to get a tool the VM does not ship, and the binary must be built for:

  • Ubuntu 24.04 LTS, x86_64, glibc 2.39 (kernel 6.12)
  • Rust target x86_64-unknown-linux-gnu, or x86_64-unknown-linux-musl for a fully static build, which is the safer choice
  • Go: GOOS=linux GOARCH=amd64 CGO_ENABLED=0

Commit it executable (git update-index --chmod=+x if needed); the deploy preserves the mode. You cannot install packages into the VM. Already on PATH: nu {{ nu_version }}, http-nu {{ http_nu_version }}, step (keys, JWT/JWE, and other crypto beyond nushell's hash builtins), caddy, git, bat.
